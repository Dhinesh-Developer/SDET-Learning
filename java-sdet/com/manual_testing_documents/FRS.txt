# 1. Introduction

## 1.1 Purpose

The purpose of this Functional Requirements Specification is to define the functional behavior of the OpenCart e-commerce application, including customer-facing shopping functionality and administrative store-management functionality.

The document will provide the functional requirements necessary for understanding, designing, testing, and validating the application's expected behavior.

# 4. Now the important part: Functional Requirements

This is where I want you to learn properly.

Don't write:

> "Login page should work."

That's **not a professional requirement**.

Instead:

## FR-ACC-001 — Customer Login

**Description**

The system shall allow a registered customer to authenticate using valid email address and password.

### Preconditions

1. Customer account must exist.
2. Customer must be on the login page.
3. Customer account must be eligible for login.

### Expected Behavior

When valid credentials are submitted:

```text
Email
   +
Password
   ↓
Submit
   ↓
System validates credentials
   ↓
Successful authentication
   ↓
Customer account/session established
```

### Validation

The system should validate:

* Email is provided.
* Password is provided.
* Email format is valid.
* Credentials are valid.

### Negative Behavior

The system should appropriately handle:

* Invalid email.
* Invalid password.
* Empty email.
* Empty password.
* Invalid email format.
* Non-existing account.

# 5. Requirement ID System

We're going to use a professional naming convention.

```text
FR-ACC-001
```

means:

```text
FR     → Functional Requirement
ACC    → Account Module
001    → Requirement number
```

For example:

| Requirement ID | Feature               |
| -------------- | --------------------- |
| FR-ACC-001     | Customer Login        |
| FR-ACC-002     | Customer Registration |
| FR-ACC-003     | Customer Logout       |
| FR-ACC-004     | Forgot Password       |
| FR-ACC-005     | Account Information   |
| FR-PROD-001    | Product Search        |
| FR-PROD-002    | Product Details       |
| FR-CART-001    | Add Product to Cart   |
| FR-CART-002    | Update Cart           |
| FR-CART-003    | Remove Product        |
| FR-CHK-001     | Checkout              |
| FR-CHK-002     | Shipping Method       |
| FR-CHK-003     | Payment Method        |
| FR-CHK-004     | Place Order           |
| FR-ORD-001     | Order History         |

This will become extremely useful later when we create **Traceability Matrix**.

# 6. Let's take a real OpenCart feature

Suppose you're looking at the Store Front.

You see:

```text
Search
   ↓
Enter product name
   ↓
Search
   ↓
Product results
```

We don't immediately write Selenium.

First:

### FR-PROD-001 — Product Search

**Requirement**

> The system shall allow customers to search for products using a product name or relevant search keyword.

### Preconditions

* Store Front is accessible.
* Search functionality is available.

### Input

```text
Search Keyword
```

### Expected Behavior

When a valid keyword is entered, the system should display products relevant to the search criteria.

### Negative Cases

What if the customer enters:

```text
Empty string
Random keyword
Special characters
Very long keyword
Partial product name
Uppercase keyword
Lowercase keyword
```

Now you're beginning to think like a tester.

# 7. Another real feature — Add to Cart

### FR-CART-001 — Add Product to Cart

**Requirement**

> The system shall allow a customer to add an available product to the shopping cart.

### Preconditions

* Product exists.
* Product is available for purchase.
* Store Front is accessible.

### Process

```text
Product Listing
      ↓
Select Product
      ↓
Product Details
      ↓
Select required options
      ↓
Add to Cart
      ↓
Cart updated
```

### Expected Result

The selected product should be added to the customer's shopping cart with the applicable quantity, options, and price.

### Business Rules

The system should consider:

* Product availability
* Quantity
* Product options
* Product price
* Stock availability

# 8. Now here is where SDET becomes interesting

Suppose requirement says:

> Customer can add product to cart.

A beginner writes:

```text
Test Add Product
```

A proper SDET asks:

### What exactly can go wrong?

```text
1. Add one product
2. Add multiple products
3. Add same product twice
4. Add unavailable product
5. Add product with options
6. Change quantity
7. Remove product
8. Refresh page
9. Logout/login
10. Cart persistence
```

And then:

### Boundary testing

```text
Quantity = 0
Quantity = 1
Quantity = maximum allowed
Quantity > maximum allowed
Negative quantity
```

This is why **FRS is the foundation of testing**.
